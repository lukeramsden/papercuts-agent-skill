# Contributing

Keep the skill generic and self-contained. Runtime code, references, licences
and launchers must stay under `skills/papercuts/`; an agent-skill installer may
copy only that directory. Do not add dependencies for local filesystem use.

## Checks

```bash
make check
ruff check .
# Optional SDK checks, in an isolated environment:
python3 -m pip install 'boto3>=1.40,<2' 'google-cloud-storage>=3,<4'
make test
```

The default tests never access cloud accounts. Use synthetic records, fake
credentials and stubbed provider calls. Test both minimum supported SDK versions
and current versions when changing storage requests. Test Python 3.10 and a
current Python on macOS/Linux. Changes to setup should cover interactive and
headless flows, not only the saved config format.

Before changing the storage contract, read
[adapters.md](skills/papercuts/references/adapters.md). Do not weaken conditional
writes or treat errors as missing data. Schema changes need an explicit version
and migration story; unknown formats must fail visibly.

## Live checks

Only with permission, use a dedicated test namespace/bucket/prefix and run:

```bash
/path/to/skill/papercuts doctor --write-test
```

It creates, conditionally changes and deletes one diagnostic object. It does
not change records. Check cleanup; versioning/soft-delete may retain old object
versions. A cloud-account owner can additionally run synthetic lifecycle tests
in an isolated destination. Do not commit provider credentials, real records,
exports, unredacted SDK errors or screenshots of sensitive configuration.

Live tests are not part of public PR CI. Do not give untrusted PR code cloud
credentials. Passing mocks is not a claim of live provider compatibility.

## Release checklist

1. Run tests without optional packages, with current SDKs, and with the declared
   minimum SDK versions. Run compile/lint and standalone-copy checks.
2. Confirm relative skill links work and launchers are executable.
3. Update CLI version and CHANGELOG; document validation limits accurately.
4. Review the Git diff and tracked file list for secrets, company identifiers,
   local paths, virtual environments, records and generated bytecode.
5. Commit, push and wait for CI. Tag the reviewed commit and create a GitHub
   release with notes and an optional skill-only archive/checksum.
6. Verify discovery with the Skills CLI. GitHub publication is not an npm/PyPI
   release; do not claim a registry package exists.

Dependencies installed by setup use bounded version ranges, not a lockfile.
Consumers who require reproducible dependency resolution should bake approved,
locked SDK versions into their own environment/image and avoid runtime installs.

## Security reports

Use GitHub's private vulnerability reporting if enabled, or contact the
maintainer privately before disclosing a vulnerability. Do not put secrets or
real feedback content in a public issue. See [SECURITY.md](SECURITY.md).
